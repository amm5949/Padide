# سند تحلیل، معماری، طراحی و کیفیت سامانه مدیریت مجوزها

**مشتری:** شرکت پخش پدیده پایدار  
**نسخه:** ۱.۰، نمونه رابط کاربری — ۱۸ نوامبر ۲۰۲۶  
**مرجع:** شش تصویر ضمیمه‌شده رابط موجود  
**قید اصلی:** رنگ تیره تصویرها حاصل Dark Reader است؛ تم مبنا **روشن** است.  
**وضعیت:** طراحی و سورس نمونه تحویل شده است؛ اتصال Backend و تأیید Business Rules انجام نشده است.

## ۱. تحلیل تصویر به تصویر

### تصویر ۱ — «لیست درخواست های اعتبار-2.png»

- **بخش:** فهرست درخواست‌های اعتبار با جزئیات بازشده یک ردیف.
- **سرستون‌ها:** ردیف، کد مشتری، نام مشتری، کد شعبه، سقف اعتبار، کل خرید، خرید ۳ ماه گذشته، عملیات و کنترل باز/بسته‌کردن جزئیات.
- **آیتم بازشده:** کد، عنوان جزئیات کامل و فیلدهای مرتبط با مشتری، وضعیت مالکیت، گروه مشتری، فروش، بدهی، چک‌ها، تخفیف‌ها، شرایط و یادداشت‌ها.
- **عملیات مشاهده‌شده:** دکمه «محاسبه»، بدون نمایش فرمول یا نتیجه عملیات؛ نمی‌توان فرض کرد این عملیات «تأیید اعتبار» است.
- **حفظ‌شده:** داده‌های جدول، کل فیلدهای مشخص، شمارش رکورد و امکان ورود به جزئیات.
- **تغییر طراحی:** جزئیات گسترده از زیر ردیف به `/admin/credit/[id]` منتقل شد؛ در موبایل کارت جای جدول می‌گیرد. جست‌وجو، فیلتر وضعیت، مرتب‌سازی تاریخ و صفحه‌بندی افزوده شد.

- **جزئیات:** مبلغ چک، تاریخ سررسید، راس، وضعیت، نام فروشنده، وضعیت چک، گروه محصول.

### تصویر ۶ — «1- مدیریت چک ها.png»

- **بخش:** همان فهرست چک‌ها در حالت بسته، **۵ رکورد نمایشی در تصویر**.
- **نیازهای افزوده:** جست‌وجو بر اساس شناسه، شماره چک و گروه مشتری؛ فیلتر وضعیت؛ ترتیب تاریخ؛ صفحه‌بندی؛ جزئیات مستقل.
- **حفظ‌شده:** همه ستون‌های معنادار، ردیف‌ها و پیوند به مشخصات تکمیلی.

> **مرزبندی شواهد:** تصاویر موجود درباره چرخه رسیدگی، قوانین پذیرش اعتبار، فرمول «محاسبه»، سطوح تأیید، ذخیره‌سازی PDF، نوع تقویم، واحد مبالغ و APIها مدرکی ارائه نمی‌کنند. این موارد به شکل پیش‌فرض کسب‌وکاری پیاده‌سازی نشده‌اند. وضعیت‌های نمونه در این پروژه برچسب پیشنهادی و ساختگی هستند.

### مرحله ۵ — بازبینی

مرحله پنج فیلد جدیدی ندارد. خلاصه تمام فیلدها را نمایش می‌دهد و امکان برگشت و اصلاح فراهم می‌کند.

**تصمیم طراحی درباره Validation:** برای امکان تست UI، کد مشتری، نام مشتری و کد شعبه به‌صورت **نمونه** اجباری‌اند. این انتخاب قانون تجاری نهایی نیست؛ پس از تأیید کارفرما با Zod schema نسخه API همسان می‌شود. مبالغ و تعدادها به عنوان رشته‌های عددی غیرمنفی پیش‌اعتبارسنجی می‌شوند؛ درصدها از نظر سقف و کف کسب‌وکاری فعلاً محدود نشده‌اند، چون در یکی از تصاویر حتی مقدار ۱۲۰٪ وجود دارد. واحد پول عمداً مشخص نشده است.

**تغییر نسبت به پیشنهاد اولیه:** مسیرها حفظ شده‌اند تا فهم ساختار برای تیم ساده بماند؛ فقط زیرساخت `layout.tsx` در سطح `/user` و `/admin` نقش Shell و بررسی نقش نمایشی را بر عهده دارد. صفحه لاگ Audit جداگانه نساخته‌ایم تا کارفرما درباره نیاز گزارش‌گیری و مجوزهای آن تصمیم بگیرد.

## ۵. Design System

| توکن | Light | Dark | کاربرد |
|---|---|---|---|
| Background | `#F5F7FB` | `#101727` | پس‌زمینه اصلی |
| Card | `#FFFFFF` | `#1A2437` | کارت و پنل |
| Text | `#1B2944` | `#E9EEF9` | متن اصلی |
| Primary | `#3548B9` | `#8A9AFC` | CTA و ناوبری فعال |
| Secondary | `#EEF2FF` | `#283456` | تأکید ملایم |
| Border | `#E5EAF2` | `#344159` | تفکیک نواحی |
| Success | `#168263` | `#49CBA5` | موفقیت |
| Warning | `#A96607` | `#FFC06A` | در انتظار |
| Danger | `#CA3B4C` | `#FF8394` | خطا/رد |

- **تایپوگرافی:** Vazirmatn در صورت تأمین فایل مجاز و self-host؛ تا آن زمان Tahoma/فونت سیستم. تیتر صفحه ۲۰ تا ۲۴px، متن اصلی ۱۴px، توضیحات ۱۲–۱۳px، ارتفاع خط ~۱.۸.
- **Spacing:** سیستم افزایشی بر مبنای ۴px؛ نمونه‌ها ۸، ۱۲، ۱۶، ۲۰، ۲۴، ۳۲ و ۴۰px.
- **Radius:** کنترل ۱۰px، دکمه ۱۲px، کارت ۱۶px، Hero برابر ۲۴px.
- **Shadow:** حداقلی و مناسب سامانه مالی؛ عمدتاً Border به‌جای سایه سنگین.
- **Control sizes:** ارتفاع دکمه و فیلد حداقل ۴۴px. Focus حلقه واضح، Hover ملایم، Disabled کاهش کنتراست همراه با غیرفعال‌بودن واقعی، Loading برای عملیات Async.
- **فرمت‌های عددی:** ارقام ورودی نرمال‌سازی و مبالغ هر ۳ رقم گروه‌بندی می‌شوند. **واحد پول در فرم و جدول تعیین نشده است.**
- **وضعیت‌ها:** Badge همراه متن و آیکون، نه فقط رنگ. در انتظار، تأیید، رد و نیازمند اصلاح، مشروط به نظر کارفرما.
- **RTL:** سند `lang=fa dir=rtl` و کلاس‌های logical مثل `start`, `end`, `ps`, `pe`, `text-start`. برای اعداد شناسه، مسیر فایل و شماره چک از `dir=ltr` استفاده شده است.
- **تم:** `Light` پیش‌فرض؛ `Dark` و `System` اختیاری. کلیدهای مرورگر جداگانه برای کاربر و مدیر؛ در محصول نهایی ذخیره در پروفایل.

### راهبرد Wireframe و Layout

**دسکتاپ:** سایدبار ثابت سمت راست با عرض ~۲۷۰px؛ هدر چسبیده بالای محتوای اصلی؛ کارت‌های خوانا و جدول کامل.  
**موبایل:** هدر فشرده، سایدبار کشویی، ناوبری پایین چهار نقطه دسترسی، کارت‌های رکورد به‌جای جدول، فیلدهای تک‌ستونی.  
**تبلت:** بدون جدول فشرده، کارت‌های نمایش رکورد + فیلترهای چندردیفه.  
**فرم اعتبار:** Stepper افقی پنج‌مرحله‌ای با نشانگرهای کوتاه؛ جمع‌بندی فیلدها در آخر؛ فیلدهای توضیحات در عرض کامل.

| Stepper اعتبار | حرکت به جلو فقط پس از Validation مرحله | خطا کنار فیلد، بازگشت آزادانه |
| مبلغ | حذف نویسه‌های غیرعددی و گروه‌بندی ارقام | قوانین سقف/کف مالی اعمال نشده است |

| ThemeSelector | Light/Dark/System | localStorage با Scope نقش |

Data source mock مستقل از UI است و در محصول نهایی می‌توان جای آن را با Service/Repository دریافت‌کننده API عوض کرد. منطق تصمیم‌های اجرایی باید در سرور باشد؛ Frontend فقط policy result و action availability را نمایش دهد.

### APIهای پیشنهادی (غیرپیاده‌سازی‌شده)

| Contract | عملیات | نکته |
|---|---|---|
| `GET /api/me` | کاربر، نقش، مجوزها، تم | سشن امضاشده |
| `GET /api/credits` | فهرست اعتبار، صفحه‌بندی/فیلتر | محدوده دسترسی سرور |
| `POST /api/credits` | ثبت اعتبار | schema و idempotency key |
| `GET /api/credits/:id` | جزئیات اعتبار | owner/role check |
| `POST /api/credits/:id/decisions` | تصمیم مدیریت | RBAC + version check + audit |
| `GET /api/checks` / `POST /api/checks` | لیست/ثبت چک | قوانین چک مستقل |
| `GET /api/checks/:id` | جزئیات چک | owner/role check |
| `POST /api/checks/:id/decisions` | تصمیم چک | تراکنش و audit |
| `POST /api/statements` | ارسال PDF | storage امن + scan + size limits |
| `GET /api/statements/:id` | متادیتا و وضعیت | role check |
| `POST /api/statements/:id/decisions` | بررسی سند | audit + versioning |
| `GET /api/statements/:id/download` | دسترسی مجاز به PDF | لینک کوتاه‌عمر یا streaming امن |
| `PATCH /api/me/preferences` | تم و ترجیحات | data validation |

**همه endpointهای فوق پیشنهادی هستند؛ تنها `upload-client.ts` با تنظیم Endpoint قابلیت ارسال به سرویس واقعی را خواهد داشت و هیچ API سروری در این ریپو ارائه نشده است.**

## ۱۰. معماری PWA و امنیت

- App Router manifest، icon sizes ۱۹۲ و ۵۱۲، maskable icon، حالت Standalone و Start URL عمومی.
- ثبت Service Worker فقط در Production.
- Offline shell تنها صفحه استاتیک عمومی و آیکون‌ها را cache می‌کند.
- **بدون cache runtime** برای صفحات کاربر/مدیر، API، PDF، نشست یا داده‌های بانکی.
- صفحه امن «اتصال اینترنت برقرار نیست» هنگام خرابی شبکه.
- Push notifications، Background Sync و ذخیره داده آفلاین مالی **پیاده‌سازی نشده‌اند** و نیاز به مجوز، سیاست امنیتی و UX جدا دارند.
- Production باید TLS، session verification، rate limiting، audit immutable، server-side PDF validation و storage policy داشته باشد.

## ۱۱. فهرست ابهام‌های نیازمند تصمیم کارفرما

1. واحد مبالغ چیست: ریال، تومان، یا واحد دیگری؟ آیا چندارزی لازم است؟
2. نوع تقویم UI و API چیست: جلالی، میلادی، یا ترکیبی؟ Format و timezone چگونه تعیین می‌شود؟
3. کدام فیلدهای فرم اعتبار واقعاً قابل ویرایش، الزامی یا فقط خواندنی هستند؟
4. معنای «مبلغ درخواست جدید» در برابر «مبلغ اعتبار درخواستی» چیست؟
5. معنای «سقف اعتبار» و «اعتبار مازاد» و نحوه محاسبه آن‌ها چیست؟
6. راس چک برحسب روز، میانگین وزنی یا واحد دیگری تعریف می‌شود؟ آیا کاربر آن را وارد می‌کند یا سرور محاسبه می‌کند؟
7. تفاوت «وضعیت» و «وضعیت چک» و Workflow مدیریت چیست؟
8. عملیات «محاسبه» در هر دو جدول چه تابعی اجرا می‌کند، ورودی و خروجی آن چیست، چه کسی مجاز است؟
9. نقش «نظر مالی» متعلق به چه کسی است و آیا کاربر اجازه ویرایش آن را دارد؟
10. آیا فرایند تأیید چندسطحی، ارجاع، اصلاح و بازگشت به درخواست‌کننده نیاز است؟
11. مدیرهای مختلف چه دامنه‌ای دارند: شعبه، منطقه، سقف امضا، مدیر اعتبارات یا مدیر مالی؟
12. مالکیت پرونده‌ها براساس شناسه کاربر، شعبه، مشتری یا چندین سازمان است؟
13. فرمت دقیق PDF، حداکثر حجم/تعداد، بازه زمانی و حداقل کیفیت پرینت حساب چیست؟
14. مدت نگهداری فایل‌ها، قوانین حذف، سطح مشاهده و انتقال به حسابرسی چیست؟
15. Notificationها از چه مسیرهایی ارسال شوند: درون‌برنامه، پیامک، ایمیل یا Push؟
16. قوانین عددی تخفیف‌ها، تاریخ‌ها و منفی/صفر بودن مبالغ چیست؟ (مثال ۱۲۰٪ در تصویر وجود دارد.)
17. کدام داده‌ها هنگام درخواست از ERP/CRM خواندنی‌اند و کدام را کاربر وارد می‌کند؟
18. فرایند تجدیدنظر یا اعتراض به درخواست ردشده چیست؟
19. آیا تاریخچه اصلاحات و علت تصمیم باید برای کاربر قابل مشاهده باشد؟
20. آیا سطح دسترسی مدیر به فایل PDF و داده‌های شعبه محدود است؟
